# CODING AGENT BRIEF — WhatsApp-First Sales CRM (UAE SME), Demo MVP

> Original brief as supplied by the product owner on 2026-09-17. Decisions that refine or supersede parts of it are tracked in the decision register (see `PLAN.md` / `ARCHITECTURE.md` once written) and in `CONTEXT.md` for vocabulary. Do not edit this file; record changes elsewhere.

You are the lead engineer building a demo MVP of a WhatsApp-first sales CRM for UAE SMEs. Work autonomously through the milestones below. Read this whole document before writing any code.

---

## 1. Product in one paragraph

A sales inbox with a deal pipeline for small UAE B2B sales teams (3–15 reps). Leads arrive automatically from Meta (Facebook/Instagram) lead ads, TikTok lead forms, and inbound WhatsApp; the rep replies from inside the CRM on the channel the lead came from; every message and action lands on a timeline; deals move through a pipeline; nobody forgets a follow-up. The owner buys it; the rep must like it. The core adoption rule: **the rep never re-enters data they already typed somewhere else.**

North star for this build: **viewability-to-client.** Every milestone ends with something a non-technical client can see and touch on a deployed URL. A milestone is not done until its demo script runs cleanly.

## 2. Locked decisions (do not relitigate)

- Market: UAE, general SME B2B. No vertical specialisation.
- Language: English UI only. Design the i18n layer so Arabic/RTL can be added later (all strings externalised, no hard-coded LTR layout assumptions), but do not build Arabic now.
- Currency: AED everywhere. VAT 5%. TRN (Tax Registration Number) on quotes.
- v1 channels: WhatsApp (Meta Cloud API), Meta Lead Ads (FB/IG), TikTok lead forms, email (Gmail OAuth), manual entry, CSV import.
- Deferred to v2 (do NOT build): Google Ads, Arabic UI, marketing automation, AI features, invoicing/e-invoicing, workflow builder, telephony, custom objects, native mobile apps.
- WhatsApp: official Cloud API only. For the demo use Meta's free **test phone number** (up to 5 verified recipients). Never implement or suggest unofficial WhatsApp Web scrapers.
- Meta Lead Ads: developer app in **development mode**, leads generated via Meta's **Lead Ads Testing Tool**. No App Review in this phase.
- TikTok: adapter interface + stub only in this phase; real integration later.
- Demo strategy: a **Simulator** (internal control panel + API) generates fake leads and messages through the same ingestion path as real adapters. The simulator is a permanent feature, not throwaway.

## 3. Stack (use exactly this unless blocked)

- **Language:** TypeScript (strict), Node 20+.
- **Monorepo:** pnpm workspaces + Turborepo. Packages: `apps/api`, `apps/web`, `packages/core` (domain logic, pure TS, no I/O), `packages/db` (Prisma schema + client), `packages/adapters` (channel adapters), `packages/shared` (types, zod schemas, event contracts).
- **API:** Fastify, zod for validation, OpenAPI generated from routes.
- **DB:** PostgreSQL 15+ via Prisma. All tables carry `workspace_id` (multi-tenant from day one, row-level scoping enforced in a repository layer, never in route handlers).
- **Queue:** BullMQ on Redis. Webhooks must return 200 in <200ms and enqueue; all processing happens in workers.
- **Realtime:** Server-Sent Events from `apps/api` to `apps/web` (simpler than WebSockets, sufficient here). Every domain event that changes the inbox or pipeline is pushed.
- **Web:** React 18 + Vite + TypeScript, TanStack Router + Query, Tailwind, shadcn/ui components. Responsive; every screen must be usable at 390px width.
- **Auth:** email + password with sessions (Lucia or equivalent); magic links are fine. Keep it simple; no OAuth providers for login in v1.
- **PDF:** `@react-pdf/renderer` or Playwright-to-PDF for quotes.
- **Testing:** Vitest for unit (core package must be >80% covered), Playwright for the demo scripts (each milestone's demo is an e2e test).
- **Infra:** Docker Compose for local (Postgres, Redis, api, web, worker). One-command deploy target: Fly.io or Railway (your choice; document it). `ngrok` or Cloudflare Tunnel for local webhook testing; document the setup.
- **Config:** all secrets via env vars; ship `.env.example` with every variable documented.

## 4. Domain model

Implement in `packages/db/prisma/schema.prisma` and mirror as zod types in `packages/shared`. All IDs are UUIDv7. All tables have `workspace_id`, `created_at`, `updated_at`; soft-delete via `deleted_at` where noted.

### Entities

- **Workspace** — the tenant. `name`, `currency` (default "AED"), `vat_rate` (default 5.00), `trn`, `timezone` (default "Asia/Dubai").
- **User** — `workspace_id`, `email`, `name`, `role` (`owner` | `manager` | `rep`), `is_active`.
- **Lead** — an unqualified inbound. `source` (`meta_leadads` | `tiktok` | `whatsapp` | `email` | `manual` | `csv` | `simulator`), `external_id` (unique per source, for idempotency), `raw_payload` (jsonb), `name`, `phone_e164`, `email`, `company_name`, `message`, `status` (`new` | `contacted` | `qualified` | `disqualified` | `converted`), `disqualify_reason`, `assigned_to` (User), `converted_contact_id`, `converted_deal_id`, `received_at`.
- **Contact** — a real person. `first_name`, `last_name`, `phones` (jsonb array of `{e164, label, is_whatsapp}`), `emails` (jsonb array), `job_title`, `company_id`, `source`, `notes`, `owner_id`. Unique index on `(workspace_id, primary phone)`.
- **Company** — `name`, `trade_license_no`, `trn`, `emirate` (enum of 7 emirates), `jurisdiction` (`mainland` | `free_zone`), `free_zone_name`, `website`, `address`, `owner_id`.
- **Pipeline** — `name`, `is_default`. Seed one per workspace.
- **Stage** — `pipeline_id`, `name`, `position`, `type` (`open` | `won` | `lost`), `probability` (0–100).
- **Deal** — `title`, `contact_id`, `company_id`, `pipeline_id`, `stage_id`, `value_aed` (decimal 14,2), `expected_close_date`, `owner_id`, `source`, `lost_reason`, `closed_at`, `last_activity_at`. Stage changes go through the state machine in `packages/core` (see §5) and are logged as `StageTransition` rows: `deal_id`, `from_stage_id`, `to_stage_id`, `by_user_id`, `at`.
- **Activity** — append-only timeline. `subject_type` (`lead` | `contact` | `deal`), `subject_id`, `type` (`note` | `message_in` | `message_out` | `email_in` | `email_out` | `call` | `meeting` | `stage_change` | `task_done` | `quote_sent` | `system`), `body`, `metadata` (jsonb), `user_id`, `occurred_at`. Never update or delete rows.
- **Task** — `title`, `due_at`, `assigned_to`, `subject_type`, `subject_id`, `status` (`open` | `done`), `completed_at`, `origin` (`manual` | `auto_stale` | `auto_lead`).
- **Conversation** — one per (contact-or-lead, channel). `channel` (`whatsapp` | `email`), `participant_phone_e164` or `participant_email`, `contact_id` nullable, `lead_id` nullable, `assigned_to`, `last_inbound_at`, `last_outbound_at`, `unread_count`, `service_window_expires_at` (WhatsApp: `last_inbound_at + 24h`).
- **Message** — `conversation_id`, `direction` (`in` | `out`), `channel`, `external_id` (provider message id, unique), `body`, `media` (jsonb), `status` (`queued` | `sent` | `delivered` | `read` | `failed`), `error`, `sent_by_user_id`, `occurred_at`.
- **Quote** — `deal_id`, `number` (per-workspace sequence, format `Q-YYYY-0001`), `line_items` (jsonb: description, qty, unit_price_aed), `subtotal_aed`, `vat_rate`, `vat_amount_aed`, `total_aed`, `valid_until`, `status` (`draft` | `sent` | `accepted` | `rejected`), `pdf_url`.
- **ChannelConnection** — per workspace: `type` (`whatsapp_cloud` | `meta_leadads` | `tiktok_leads` | `gmail`), `status`, `config` (jsonb, encrypted at rest for tokens), `external_account_id`.
- **AssignmentRule** — `strategy` (`round_robin` | `manual`), `eligible_user_ids`, `last_assigned_user_id`.

### Rules

- Phone numbers are normalised to E.164 on write (`libphonenumber-js`, default region AE). Identity resolution across channels is by phone.
- A Lead converts into a Contact (+ optional Company) + Deal in one transaction; the Lead is marked `converted` and linked; its Conversation (if any) is re-pointed to the Contact.
- Deleting is soft; Activities and Messages are never deleted.

## 5. State machines (put in `packages/core`, pure functions, fully unit-tested)

**Lead:** `new → contacted → qualified → converted`; `new|contacted|qualified → disqualified` (reason required). `converted` and `disqualified` are terminal.

**Deal:** any `open` stage → any other `open` stage; any `open` stage → `won` or `lost` (`lost_reason` required; `closed_at` set). `won`/`lost` → reopen to an `open` stage allowed only for `owner`/`manager` and logs a `system` activity. Every transition writes a `StageTransition` row and an Activity.

**WhatsApp service window:** an outbound free-form message is allowed only if `now < service_window_expires_at`. Outside the window, only template sends are allowed; the UI must show the window state and disable free-form input with an explanation.

## 6. Ingestion architecture (the core of the demo)

All inbound sources normalise to internal events defined in `packages/shared/events.ts`:

```ts
type LeadReceived = {
  type: "lead.received";
  workspaceId: string;
  source: LeadSource;
  externalId: string;
  receivedAt: string;
  fields: Record<string, string>;
  raw: unknown;
};
type MessageReceived = {
  type: "message.received";
  workspaceId: string;
  channel: "whatsapp" | "email";
  externalId: string;
  from: string;
  body: string;
  media?: Media[];
  occurredAt: string;
  raw: unknown;
};
type MessageStatusChanged = {
  type: "message.status";
  externalId: string;
  status: MessageStatus;
  error?: string;
};
```

Each adapter in `packages/adapters/<name>` implements:

```ts
interface InboundAdapter {
  name: string;
  verifyWebhook(req): boolean; // signature / verify-token
  parseWebhook(req): InboundEvent[]; // no I/O, no DB
}
interface OutboundAdapter {
  sendMessage(conn: ChannelConnection, msg: OutboundMessage): Promise<{ externalId: string }>;
}
```

Pipeline: `POST /webhooks/:adapter` → verify → parse → enqueue events → worker runs `ingestEvent()` in `packages/core` → creates/updates Lead/Conversation/Message/Activity → runs assignment → emits SSE.

Idempotency: every event keyed on `(source, externalId)`; duplicates are no-ops.

**Adapters to build:**

1. `simulator` — no webhook; exposes `POST /dev/simulate/lead` and `POST /dev/simulate/message` (guarded by `DEMO_MODE=true`). Produces realistic UAE fake data (Arabic and English names, +971 numbers, Dubai/Abu Dhabi/Sharjah companies, plausible enquiries).
2. `whatsapp-cloud` — Meta WhatsApp Cloud API. Webhook verify token + `X-Hub-Signature-256`. Inbound text/media/status events. Outbound text + template sends. Unknown number → new Lead with `source=whatsapp`.
3. `meta-leadads` — `leadgen` webhook → fetch `GET /{leadgen_id}` via Graph API with Page token → `LeadReceived`. Include a CLI/script that walks through connecting a Page in dev mode.
4. `tiktok-leads` — interface implemented, `parseWebhook` handles TikTok's documented payload shape, everything else throws `NotImplemented` with a clear message.
5. `gmail` — Gmail OAuth, watch/poll for threads, inbound → `MessageReceived` with `channel=email`; outbound via Gmail API so mail comes from the rep's address.

## 7b. Parallel execution plan (MANDATORY)

The milestones above are the **demo order**, not the build order. You have access to subagents. Anything that can be built in parallel MUST be built in parallel; only true dependencies are allowed to serialise work. Plan the work as a dependency graph, then execute it in waves. Within a wave, spawn one subagent per independent workstream and let them run concurrently; between waves, integrate, run the full test suite, and only then start the next wave.

### Contracts first, then fan out

The single thing that makes parallel work safe is that shared contracts are frozen before anyone builds against them. Wave 0 produces those contracts; every later wave consumes them without changing them (a change to a contract is a coordinated task for the orchestrator, never a side effect of one subagent's work).

**Wave 0 — Contracts (one agent, serial, short):**

### Rules for parallel work

- Before each wave, the orchestrator writes `WAVE_N.md`: the subagents, their exact scope, the files/packages each owns, the contracts they consume, and their definition of done. Two subagents never own the same file.
- Subagents work on separate branches and open PRs into an integration branch; the orchestrator merges, resolves conflicts, and runs the full suite.
- A subagent that discovers it needs a contract change stops, reports it, and the orchestrator applies the change across all affected workstreams before anyone continues.
- Independent long-running chores (recording Meta payload fixtures, writing seed data, writing docs, building the Playwright harness) are always farmed out in parallel with feature work, never done inline by the orchestrator.
- If the human's Meta setup is incomplete, that never blocks a wave: all Meta-dependent work is built against recorded fixtures and switched to live at the integration checkpoint.
- In `PLAN.md`, draw the dependency graph explicitly (Mermaid) and list, per wave, what runs concurrently and the estimated wall-clock time assuming full parallelism. Optimise for shortest wall-clock time to each demo, not fewest agents.

## 8. Engineering standards

- Strict TypeScript, no `any` without a comment justifying it. ESLint + Prettier enforced in CI.
- Domain logic lives in `packages/core` as pure functions and is unit-tested. Route handlers are thin.
- Every DB query is scoped by `workspace_id` through the repository layer. Write one integration test proving cross-tenant reads are impossible.
- Webhook handlers: verify signature, enqueue, return 200. Never process inline.
- All money is `decimal`, never float. All times stored UTC, displayed in workspace timezone.
- Log structured JSON (pino). Every inbound event logs `source`, `externalId`, `workspaceId`, outcome.
- Migrations are forward-only and reviewed; never edit a migration after merge.
- Accessibility baseline: keyboard-navigable kanban and inbox; labelled inputs.
- Seed and simulator data must look real for a UAE audience (names, companies, +971 numbers, enquiries like "need 200 sqm office fit-out in JLT").
- Keep `README.md` (setup in <10 minutes), `DEMO.md` (all demo scripts), `ARCHITECTURE.md` (diagram of ingestion path, domain model, decisions) current with every milestone.

## 9. What NOT to do

- No Arabic/RTL UI work, no AI features, no marketing automation, no Google Ads, no invoicing, no native mobile apps, no workflow builder, no custom fields engine (hard-coded UAE fields are fine).
- No unofficial WhatsApp integrations of any kind.
- Do not gold-plate reporting; the dashboard is five widgets, not a report builder.
